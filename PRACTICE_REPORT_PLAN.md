# Отчёт по преддипломной практике — план и анализ

Состояние от 2026-06-04. Это **план** отчёта по производственной (преддипломной)
практике под проект `cfd-platform`, построенный по образцу отчёта Бердышева К.Д.
(РК6, 2026). Не сам отчёт — каркас + что в каждый раздел записать и из какого
готового артефакта он берётся.

## Короткий ответ на вопрос «достаточно ли сборки solver-образов и тестов»

**Нет — это мало.** «Сборка образов + тесты» = один-два подраздела из восьми.
Отчёт по практике (по жанру, как у Бердышева) = **вся инженерная сборка
действующего программного комплекса**. У тебя система **богаче**, чем у
Бердышева: не один backend+UI, а многокомпонентная HPC-платформа (кастомный
планировщик, F-graph extraction для 3 классов решателей, 3 solver-образа,
реальный multi-AZ кластер). Материала на отчёт — с запасом; проблема будет
обратная — что **сократить**.

## Ключевой принцип жанра (вывод из примера Бердышева)

Отчёт по преддипломной практике = **«построение действующего комплекса (MVP)»**.
Исследовательская часть остаётся в ВКР. У Бердышева это сказано прямо:

> «Построенная система носит характер MVP… оптимизация инференса средствами
> TensorRT (FP16/INT8) **является предметом исследования ВКР**… Полученные
> результаты послужат основой для исследовательской части ВКР.»

То есть у него: **практика = собрал систему**, **ВКР = research/оптимизация поверх**.

**Твой раскол — точно такой же и идеально ложится:**

| | Практика (этот отчёт) | ВКР / диплом |
|---|---|---|
| Содержание | **Сборка платформы** cfd-platform: backend, scheduler+алгоритмы, F-graph extraction, solver-образы, кластер, деплой, E2E-smoke | **Эксперимент**: гипотеза, 60 прогонов (N=16 + N=32), статистика, Table 5.1 |
| Главы диплома | ≈ Глава 3 (Архитектура) + Глава 4 (Реализация) | Глава 1 (литобзор) + Глава 2 (постановка/гипотеза) + Глава 5 (результаты) |
| Уже есть в репо | весь код + [STATUS.md](STATUS.md), [EXTRACTION.md](EXTRACTION.md), [CLUSTER.md](CLUSTER.md) | [EXPERIMENT.md](EXPERIMENT.md), [BENCHMARKS.md](BENCHMARKS.md), [RELATED_WORK.md](RELATED_WORK.md), [THESIS.md](THESIS.md) |

Практический отчёт фактически = черновик глав 3–4 ВКР (так и задумано — «частично
или полностью практическая часть диплома»). Пиши его так, чтобы потом перенести
в диплом почти дословно.

## Что НЕ включать в отчёт по практике (это в ВКР)

- Гипотезу H1/H2 (MM gain растёт с плотностью F и с N).
- Дизайн эксперимента (3×3×6, N=16/32, обоснование числа рангов/гранулярности).
- Статистику (Shapiro-Wilk, t-CI/bootstrap, paired-тесты, n=5, односторонние).
- Численные результаты, Table 5.1, графики gain(ρ).
- Литобзор конкурентов (Volcano/Fluence/Xie 2026) — это глава 1 ВКР.

В практике можно одной фразой во Введении/Заключении сказать «построенный
комплекс служит основой для сравнительного эксперимента над алгоритмами
размещения, рассматриваемого в ВКР» — ровно как Бердышев упомянул TensorRT.

## Рекомендуемая структура отчёта (под cfd-platform)

Объём-ориентир: ~20–24 стр. (как у Бердышева — 22). 2–4 листинга кода.

### Задание (формулировка для бланка, 3 пункта — как у Бердышева)
1. Изучение предметной области (MPI-параллелизм в инженерных расчётах, scheduling в Kubernetes) и формирование требований к платформе.
2. Проектирование архитектуры и развёртывание инфраструктуры (кластер, MPI Operator, хранилища, CI/CD образов).
3. Реализация серверной части, планировщика и конвейера извлечения коммуникационного графа.

### Введение (3–5 стр.)
- Актуальность: инженерные расчёты (CFD/FEM) — это MPI-параллелизм; перенос HPC в Kubernetes; «топологическая слепота» kube-scheduler → накладные расходы на MPI-коммуникацию в multi-AZ.
- Объект: размещение MPI-рангов по узлам K8s-кластера.
- Предмет: программные решения для приёма задачи, извлечения графа коммуникации F(i,j), размещения рангов и сбора профиля MPI.
- Цель: спроектировать и реализовать платформу запуска параллельных расчётов с topology-aware планировщиком.
- Задачи: требования → архитектура → инфраструктура/деплой → extraction-конвейер → планировщик → backend → solver-образы+CI → smoke-валидация.
- Практическая значимость: действующий комплекс = основа для исследовательской части ВКР (сравнение алгоритмов размещения).

### 1. Постановка задачи (1–2 стр.)
- Что строим: web-платформа, принимающая архив расчёта (OpenFOAM/OpenRadioss/Code_Aster), извлекающая F-граф, создающая MPIJob с выбором алгоритма размещения, профилирующая MPI (mpiP) и отдающая отчёт.
- Роли/сценарии: исследователь (submit + monitor), оркестратор-бенчмарк (Python, программный запуск). 3 решателя = 3 класса плотности F-графа.
- Функциональные требования: загрузка кейса → two-phase (extraction Job → MPIJob); выбор scheduler/алгоритма; сбор mpiP-отчёта в общий PVC; статусы.
- Нефункциональные: модульность (3 Go-модуля), контейнеризация всех служб, воспроизводимость (dedicated CPU + tc qdisc), Burstable QoS без CPU-limits.
- Стек: Go (chi + dynamic/typed k8s client), React+TS+Vite, kubeflow MPI Operator v2beta1, kind, LLNL mpiP, GHCR, tc netem.

### 2. Краткий отчёт о выполненных работах

**2.1 Анализ требований и сценариев** (≈1 стр.)
Use cases (submit/monitor/collect; программный прогон). Логическая модель (Simulation: id/type/np/scheduler/algorithm/status). Формальная модель размещения: минимизировать Σ F(i,j)·L(π(i),π(j)) — QAP. → из [README.md](README.md), domain-модели.

**2.2 Архитектура системы** (≈2 стр., с компонентной схемой)
5 слоёв: Frontend → Backend(REST) → MPI Operator(MPIJob CRD) → solver-поды(+mpiP) → topology-aware extender сбоку. Общие PVC (configs/results/scheduler-graphs). 3 Go-модуля (backend / scheduler / pkg/decomp). → схема из [README.md](README.md), [STATUS.md](STATUS.md).

**2.3 Конвейер извлечения F-графа (центральный инженерный вклад)** (≈2–3 стр.)
Единый pipeline для 3 классов решателей:
- OpenFOAM: `decomposePar` → `processor*/constant/polyMesh/boundary` → парсер;
- OpenRadioss: sed-patch `IDB_METIS=1` → METIS-граф → `gpmetis` → парсер;
- Code_Aster: `medpartitioner --create-boundary-faces` → joints (MEDLoader) → edge-list.
Типизированные парсеры в `pkg/decomp` (16 тестов). → из [EXTRACTION.md](EXTRACTION.md), `pkg/decomp/`, `scheduler/cmd/extract-*`.
**Листинг-кандидат:** формат edge-list / парсер boundary.

**2.4 Topology-aware планировщик** (≈2 стр.)
Реализован как **Kubernetes Scheduler Extender** (HTTP `/prioritize`) — почему не in-tree (go.mod-зависимости kube-scheduler). 3 алгоритма: random (baseline), greedy (online O(n²)), Müller-Merbach (offline QAP-эвристика). Маршрутизация по лейблу пода. → из `scheduler/`.
**Листинг-кандидат:** целевая функция `Cost()` или ядро MM (`scheduler/algorithms/`).

**2.5 Серверное приложение (backend)** (≈2 стр.)
Go + chi + dynamic/typed k8s-клиент. Two-phase оркестрация: распаковка tar.gz → extraction Job → ожидание → MPIJob. Конструирование MPIJob: Burstable QoS (без CPU-limits, по Xie 2026), worker anti-affinity (1 ранг/нода), лейбл алгоритма, mpiP через LD_PRELOAD + сбор отчёта. → из `backend/internal/`.
**Листинг-кандидат:** конструкция MPIJob spec или solverCommand (mpirun-обёртка).

**2.6 Solver-образы и CI/CD** (≈2 стр.) ← *вот сюда «сборка образов»*
3 multi-stage образа (OpenFOAM 2306 / OpenRadioss 2025.10 / Code_Aster 15.5.2), в каждый вкомпилирован LLNL mpiP (`libmpiP.so`) на совместимом OpenMPI ABI + extract-бинарь. Интеграция с mpi-operator: openssh-server + ssh-config (StrictHostKeyChecking/StrictModes) для ssh launcher↔worker. CI: матрица GH Actions → GHCR (free-disk + swap для тяжёлой сборки Code_Aster ~90 мин, GHA-кэш). → из `docker/`, `.github/workflows/build-images.yml`, [STATUS.md](STATUS.md).
Сюда же — **smoke-тесты** образов (single-node MPI Allreduce + mpiP-отчёт).

**2.7 Развёртывание кластера и валидация** (≈2 стр.)
`scripts/cluster-up.sh`: kind-кластер (1 cp + N воркеров) с эмуляцией multi-AZ через `tc qdisc netem` (3 зоны, 5/10 мс), cgroup cpuset-изоляция, RWX-хранилища (hostPath + extraMounts), установка MPI Operator, кастомный kube-scheduler + extender, локальная сборка backend. **E2E-smoke**: один MPIJob (OpenFOAM pitzDaily) сквозь backend → extraction → размещение → simpleFoam parallel → mpiP-отчёт в `/results/<id>` → парсинг. → из [CLUSTER.md](CLUSTER.md), `scripts/cluster-up.sh`.
**Листинг-кандидат:** фрагмент tc-netem или kind-config.

**2.8 Пользовательский интерфейс** (≈1 стр.)
React + TypeScript + Vite: загрузка кейса, выбор решателя/числа рангов/планировщика, список симуляций со статусами. → из `frontend/`.

### 3. Анализ результатов (≈2 стр.)
Получен действующий комплекс; все функциональные требования выполнены.
**E2E-smoke пройден** (на VM Vast.ai EPYC 9654, kind, 24 ноды, multi-AZ через tc): полная цепочка от загрузки кейса до mpiP-отчёта; парсер прочитал MPI-time. Latency-контраст между зонами подтверждён замером (a↔c ≈ 10 мс vs внутри зоны ≈ 1.4 мс). Модульность (3 Go-модуля, 3 раздельных образа) + контейнеризация → независимая разработка/деплой. Комплекс = MVP-основа для сравнительного эксперимента над алгоритмами размещения (ВКР).

### Заключение (1–2 стр.)
Перечислить достигнутое по задачам; финальная фраза — про переход к исследовательской части ВКР (эксперимент сравнения random/greedy/MM).

### Список литературы (skeleton, ~12–15 позиций)
Go; chi; Kubernetes docs; kubeflow MPI Operator; kind; LLNL mpiP; OpenFOAM (ESI 2306); OpenRadioss; Code_Aster / MEDCoupling; METIS (Karypis); React; Vite; Burkard/Dell'Amico/Martello «Assignment Problems» (QAP, Müller-Merbach); Xie 2026 (Burstable QoS — методологическая опора). Реальные эксперименты/статистику в список не тащить (это ВКР).
