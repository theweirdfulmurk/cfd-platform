# Промпт для Claude-писателя отчёта по практике

Скопируй всё ниже (от линии до линии) в свежую сессию Claude, запущенную **в корне
репозитория `cfd-platform`**. Файлы `PRACTICE_REPORT_ARCHITECTURE.md`,
`PRACTICE_REPORT_PLAN.md` и весь код должны быть доступны.

---

Ты пишешь **отчёт по производственной (преддипломной) практике** для проекта
`cfd-platform` — это инженерно-практическая часть дипломной работы студента РК-6
МГТУ им. Баумана (тема ВКР — topology-aware Kubernetes-планировщик для
параллельных инженерных расчётов). Отчёт по жанру = «построение действующего
программного комплекса»; исследование (эксперимент) остаётся в ВКР.

## Сначала изучи (в этом порядке)

1. `PRACTICE_REPORT_ARCHITECTURE.md` — детальная архитектура по фактическому коду,
   источники для цитирования (Часть B), кандидаты на листинги (Часть C) и
   **таблицу «планы vs факт»**. Это твой главный источник.
2. `PRACTICE_REPORT_PLAN.md` — структура разделов и граница «практика vs ВКР».
3. **Код репозитория** — первоисточник истины. Любое техническое утверждение
   сверяй с кодом (`backend/`, `scheduler/`, `pkg/decomp/`, `docker/`, `k8s/`,
   `scripts/cluster-up.sh`, `frontend/`). Если детали нет в брифе и в коде — не
   выдумывай её.
4. Вспомогательно: `EXTRACTION.md`, `CLUSTER.md`, `STATUS.md`, `README.md` — но
   пропускай их через таблицу «планы vs факт» (там есть устаревшие утверждения).

## Что написать

Один markdown-файл `PRACTICE_REPORT.md`, на русском, академический
нейтрально-технический стиль (как в типовых отчётах РК-6: «реализовано»,
«выполнено», без маркетинга и первого лица). Объём ~20–24 страницы.

Структура:
- **Введение** (актуальность HPC-расчётов в K8s; объект — размещение MPI-рангов по
  узлам; предмет — программные решения приёма задачи, извлечения графа F(i,j),
  размещения и сбора профиля MPI; цель; задачи; практическая значимость —
  комплекс служит основой исследовательской части ВКР).
- **1. Постановка задачи** (что строим, роли/сценарии, функц. и нефункц.
  требования, стек).
- **2. Краткий отчёт о выполненных работах** — подразделы **2.1–2.8** ровно по
  `PRACTICE_REPORT_PLAN.md` (анализ требований; архитектура; F-graph extraction;
  планировщик; backend; solver-образы+CI; кластер+smoke; UI).
- **3. Анализ результатов** (получен действующий комплекс; E2E-smoke пройден;
  модульность/контейнеризация; комплекс как MVP-основа для ВКР).
- **Заключение** (достигнутое по задачам; переход к исследовательской части ВКР).
- **Список литературы** (только реально процитированные источники из Части B).

Включи **2–4 листинга кода** (из Части C брифа), каждый с подписью «Листинг N – …».
Дай больше глубины разделам **2.3 (F-graph extraction)** и **2.4 (планировщик/QAP)**
— это уникальный методический и алгоритмический вклад.

## Жёсткие ограничения (нарушение = переписывать)

1. **Только реальная реализация.** Backend хранит состояние в **in-memory
   репозитории** за интерфейсом; хранилище — **общие PVC** (ReadWriteMany).
   **PostgreSQL, MinIO, OpenSearch, Triton, БД и object-store — НЕ упоминать** как
   часть системы (их нет в рантайме). Сверяйся с кодом перед каждым заявлением о
   компоненте.
2. **Жёсткая граница с ВКР — НЕ включать**: гипотезу; дизайн эксперимента (3×3,
   N=16/32, обоснование числа рангов/гранулярности); статистику (Shapiro-Wilk,
   t-тест, bootstrap, n=5); численные результаты, таблицы сравнения, графики
   gain(ρ); литобзор конкурентов (Volcano/Fluence/Xie). Единственное исключение —
   одна фраза про Burstable QoS без CPU-limits со ссылкой на Xie 2026 как
   методологическое обоснование в 2.5.
3. **Источники — только реальные** из Части B брифа; в список литературы вносить
   лишь те, что реально процитированы в тексте. Не выдумывать ссылки.
4. **Не выдумывать** метрики, числа, имена компонентов, версии, которых нет в коде
   или брифе.
5. **Не засорять** тело отчёта путями файлов и номерами строк (`backend/internal/…`)
   — это академический текст, а не дев-документация; имена технологий допустимы.
6. **Локализация имён и аббревиатур**: фамилии людей в тексте — **кириллицей**
   (Мюллер-Мербах, Купманс, Бекман, Се (Xie)…; «эвристика Мюллера-Мербаха»); список
   литературы — в оригинале (латиница, ГОСТ). Аббревиатуры с русским стандартом —
   русифицировать (FEM→МКЭ, CFD→ВГД); международные без стандарта — латиницей с
   расшифровкой при первом упоминании (QAP, MPI, MUMPS), не выдумывать «КЗН».
   Технологии/идентификаторы (OpenFOAM, Kubernetes, mpiP) — латиницей; имена
   процедур в листингах — латиницей (код).

## Типичные ошибки, которых избегай

- Заявить PostgreSQL/MinIO «по аналогии с примером Бердышева» — у этой системы их
  нет. Описывай свою.
- Протащить кусок эксперимента/статистики «для полноты» — это в ВКР.
- Перегрузить листингами (>4) или вставить листинг без пояснения.
- Английский там, где уместен русский (кроме устоявшихся имён: OpenFOAM, MPIJob,
  Kubernetes, mpiP и т.п.).
- Раздуть введение водой — держи плотность как в примере.

Пиши «на чистовик»: этот отчёт затем почти дословно переносится в главы 3–4 ВКР.
